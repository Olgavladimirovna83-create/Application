08_METRICS_FRAMEWORK

Purpose

The Metrics Framework defines which performance metrics the system collects, monitors, compares, and uses for analysis.

The system should not treat metrics as isolated numbers.

Each metric should be interpreted in relation to:

* the user’s broader growth objective;
* the user’s historical performance;
* the content format;
* the characteristics of the publication;
* other relevant metrics;
* and the user’s personal analytical algorithm.

The purpose of collecting metrics is to understand what is happening in the account and identify patterns that can support better growth decisions.

⸻

1. Core Principle

The system should collect and preserve the maximum amount of performance data that is legally and officially available to the user through their own Instagram account and authorised access.

The system should not intentionally restrict the dataset to a small predefined selection if additional useful metrics are available.

The complete available dataset should be preserved so that future versions of the analytical system can use information that may not yet have an obvious application.

⸻

2. Account-Level Metrics

The system should collect available metrics describing the overall performance and state of the account.

These may include:

* total followers;
* follower growth;
* followers gained;
* followers lost, if available;
* total reach;
* total impressions;
* accounts reached;
* accounts engaged;
* engagement-related metrics;
* profile visits;
* website or external link activity, if available;
* content interactions;
* and other officially available account-level metrics.

The exact available metrics may vary depending on Instagram’s API capabilities and the user’s account type.

The system should therefore be designed to adapt to the metrics actually available rather than assuming that every account will expose exactly the same dataset.

⸻

3. Publication-Level Metrics

For each individual publication, the system should collect all relevant available performance data.

Depending on the format and Instagram’s available data, this may include:

* publication date and time;
* content format;
* likes;
* comments;
* saves;
* shares;
* reach;
* impressions;
* views or plays;
* profile activity generated by the publication;
* followers gained;
* engagement;
* and other available performance indicators.

The system should preserve the relationship between each metric and the specific publication that generated it.

This allows the Analytical Engine to analyse individual content rather than only aggregate account statistics.

⸻

4. Format-Specific Metrics

Different content formats may expose different metrics or behave differently.

The system should therefore identify the format of each publication and interpret its metrics accordingly.

Examples include:

* Reels;
* carousels;
* single-image posts;
* Stories;
* and other formats supported in the future.

A Reel should not automatically be compared directly with a carousel using identical assumptions.

The system should use format-appropriate comparisons wherever possible.

⸻

5. Historical Metrics

The system should preserve historical performance data rather than replacing old values with the newest numbers.

This is essential because the Analytical Engine needs to understand change over time.

Historical data should allow the system to determine:

* whether performance is improving or declining;
* whether a metric is above or below the user’s normal level;
* whether a recent change is temporary or persistent;
* whether a content pattern repeatedly produces a particular result;
* and whether previous recommendations appear to have influenced performance.

⸻

6. Comparative Analysis

A metric should rarely be interpreted as an isolated number.

The system should compare current performance with relevant historical benchmarks.

Examples include:

Latest publication vs previous four publications of the same format

Current period vs previous period

Current metric vs user’s historical average

Specific content group vs other relevant content groups

The exact comparison methodology belongs to the Analytical Engine.

The Metrics Framework defines the availability and preservation of the underlying measurements.

⸻

7. Metric Relationships

The system should preserve the ability to analyse relationships between metrics.

For example:

* reach → followers gained;
* views → followers gained;
* likes → reach;
* saves → reach;
* shares → reach;
* comments → reach;
* profile visits → followers gained.

The goal is not to assume that one metric automatically causes another.

Instead, the system should identify whether meaningful relationships or recurring patterns appear in the user’s own historical data.

⸻

8. Metrics and the Growth Objective

The ultimate purpose of the metrics is account growth.

However, the system should not assume that the highest-priority metric is always follower growth itself.

Intermediate metrics may provide useful information about the current state of the account.

For example:

If follower growth is weak but reach is strong, the system may investigate whether the problem lies in converting attention into profile visits or follows.

If reach is strong but likes are unusually weak, the system may identify content characteristics associated with stronger like performance.

If saves or shares are unusually strong, the system may investigate which content characteristics repeatedly generate those behaviours.

The system should therefore use metrics diagnostically.

⸻

9. Relative Performance

Absolute numbers are not sufficient for meaningful analysis.

The system should prioritise relative performance whenever appropriate.

For example:

A post receiving 1,000 likes may be highly successful for one account and weak for another.

Therefore, the system should primarily understand metrics relative to the user’s own historical performance.

Useful concepts may include:

* historical average;
* median performance;
* percentile;
* deviation from normal performance;
* performance relative to comparable content;
* and performance trend over time.

The specific statistical methods will be defined in the Analytical Engine.

⸻

10. Metric Prioritisation

The system should not permanently assign a universal ranking to all metrics.

The importance of a metric depends on:

1. the user’s current growth objective;
2. the current state of the account;
3. the historical performance of the metric;
4. relationships between metrics;
5. and the patterns identified by the Analytical Engine.

Therefore, the same metric may be highly relevant at one point and less relevant at another.

For example:

A user whose primary objective is follower growth may temporarily focus on improving content that generates strong engagement if the data suggests that this could support broader account growth.

⸻

11. Data Completeness

The system should distinguish between:

data that does not exist

and

data that has not yet been collected

and

data that Instagram does not currently make available through authorised access.

Missing data should never be silently treated as zero.

The system should preserve information about data availability so that the Analytical Engine does not make conclusions based on false assumptions.

⸻

12. Initial Synchronisation

When the user first connects their Instagram account, the system should attempt to import the maximum amount of historical performance data that is legally and technically available.

The initial target should be to obtain approximately the previous three months of relevant historical data, where Instagram makes it available.

The initial synchronisation should happen progressively in the background.

The application should not require the user to wait for the entire historical dataset to be imported before providing value.

⸻

13. Immediate Value

The system should provide useful information as soon as possible after the account is connected.

The intended sequence is:

Connect Instagram

→ Retrieve immediately available recent data

→ Show initial account statistics

→ Analyse available recent publications

→ Provide an initial analysis

→ Continue importing historical data in the background

→ Improve the analysis as additional data becomes available

The user’s first experience should therefore not depend on completing the entire historical synchronisation.

⸻

14. Continuous Data Collection

After the initial synchronisation, the system should continue collecting newly available data on a regular basis.

The intended initial model is approximately daily updating.

This allows the system to maintain an up-to-date picture of the account while gradually building a larger historical dataset.

The exact update frequency may change depending on:

* Instagram API limitations;
* technical constraints;
* cost;
* data availability;
* and future product requirements.

⸻

15. Storage Principle

The system should preserve historical analytical data for as long as reasonably useful for the product.

The purpose of long-term storage is to allow the system to identify patterns that may not be visible over short periods.

For example, a content format may appear successful over one month but reveal a completely different pattern when compared across six or twelve months.

The application should therefore avoid unnecessarily deleting historical analytical data.

Heavy media files should not be duplicated unnecessarily if they are not required for the analytical process.

The primary dataset should consist of performance metrics, content metadata, and other information required to understand and analyse the user’s content.

⸻

16. Future-Proof Design

The Metrics Framework should be designed so that new metrics can be added without redesigning the entire system.

Instagram may introduce new metrics or change the information available through its APIs.

The application should therefore treat the metric structure as extensible.

The same architecture should also allow additional platforms, such as TikTok, to be integrated in the future without fundamentally changing the analytical philosophy.

⸻

17. Core Principle

The system should follow one fundamental rule:

Collect as much relevant, legally available information as possible, preserve it, and allow the Analytical Engine to determine which information is useful for a particular question.

The Metrics Framework is therefore not responsible for deciding what the data means.

Its responsibility is to ensure that the Analytical Engine has the richest reliable dataset possible.
