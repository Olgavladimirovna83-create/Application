24_TECHNICAL_ARCHITECTURE

1. Назначение документа

TECHNICAL_ARCHITECTURE переводит логическую архитектуру продукта в техническую структуру, понятную разработчику.

Документ определяет:

* основные технические компоненты;
* границы между ними;
* потоки данных;
* API;
* фоновые процессы;
* хранение данных;
* работу аналитики;
* работу Recommendation Engine;
* взаимодействие с AI Assistant;
* обновление информации;
* требования к расширяемости;
* требования к тестированию;
* требования к надёжности.

Главный принцип:

техническая реализация должна сохранять продуктовую логику, зафиксированную в предыдущих документах, а не заставлять продукт подстраиваться под технические ограничения.

⸻

2. Основной принцип технической архитектуры

Архитектура должна быть:

* modular;
* extensible;
* testable;
* observable;
* replaceable;
* explainable.

При этом MVP не должен быть перегружен инфраструктурой.

Логически система должна быть модульной уже с первой версии.

Физически некоторые компоненты могут находиться внутри одного backend-приложения.

⸻

3. Общая техническая схема

Упрощённая структура:

EXTERNAL PLATFORM

↓

DATA CONNECTOR

↓

INGESTION

↓

DATABASE

↓

ANALYSIS SERVICES

↓

KNOWLEDGE STORE

↓

DECISION ENGINE

↓

API

↓

FRONTEND

↓

AI ASSISTANT

↓

USER ACTION

↓

EVENT / OUTCOME

↓

DATABASE

↓

LEARNING / REANALYSIS

⸻

4. FRONTEND

Frontend отвечает за пользовательский интерфейс.

Он должен:

* получать данные через API;
* отображать текущую рекомендацию;
* показывать причины;
* показывать альтернативы;
* отображать состояние анализа;
* принимать действия пользователя;
* передавать пользовательские решения обратно в backend.

Frontend не должен самостоятельно вычислять бизнес-логику рекомендаций.

⸻

5. MAIN_APPLICATION_SHELL

Основное приложение должно иметь единую оболочку.

В ней находятся основные пользовательские разделы.

Минимально:

* Home;
* Recommendations;
* Analytics;
* History;
* Assistant;
* Settings.

При этом Home остаётся главным рабочим пространством.

⸻

6. HOME

Главная страница получает уже подготовленное текущее состояние.

Например:

* primary recommendation;
* reason;
* confidence;
* alternatives;
* recent context.

Frontend не должен сам выбирать, что из этого является главным.

⸻

7. RECOMMENDATION_UI

Компонент рекомендации должен быть универсальным.

Он должен уметь отображать:

* recommendation;
* goal;
* reason;
* confidence;
* expected benefit;
* alternatives;
* available actions.

Новый тип рекомендации не должен требовать полной перестройки интерфейса.

⸻

8. ASSISTANT_UI

AI Assistant должен быть встроен в продуктовый контекст.

Он не должен существовать как полностью отдельный чат, который ничего не знает о текущем состоянии пользователя.

Ассистент должен получать контекст текущей страницы и текущей рекомендации.

⸻

9. BACKEND

Backend является центральным техническим слоем.

Он отвечает за:

* бизнес-логику;
* API;
* данные;
* аналитику;
* Recommendation Engine;
* события;
* фоновые задачи;
* AI orchestration.

⸻

10. API_LAYER

Frontend взаимодействует с backend через API.

API должен предоставлять структурированные сущности, а не возвращать сырые внутренние таблицы базы данных.

Например:

GET /recommendations/current

может возвращать:

* primary recommendation;
* alternatives;
* reasons;
* confidence;
* goal;
* context.

Конкретные URL могут измениться на этапе реализации.

Главное требование:

API должен отражать продуктовые сущности, а не внутреннюю структуру базы.

⸻

11. API_CONTRACTS

Каждый endpoint должен иметь чёткий контракт:

* входные параметры;
* обязательные поля;
* типы данных;
* возможные ошибки;
* формат ответа;
* правила авторизации.

Изменение контракта должно быть контролируемым.

⸻

12. AUTHENTICATION

Система должна иметь отдельный механизм идентификации пользователя.

Каждый запрос к приватным данным должен выполняться в контексте конкретного пользователя.

Нельзя допускать обращения к данным только по внешнему идентификатору без проверки принадлежности.

⸻

13. AUTHORIZATION

Authentication отвечает на вопрос:

«Кто пользователь?»

Authorization:

«Что этому пользователю разрешено?»

Эти уровни должны быть разделены.

⸻

14. DATABASE

Основная база должна хранить структурированные сущности.

Минимально:

* users;
* goals;
* content;
* content_features;
* performance;
* baselines;
* patterns;
* hypotheses;
* recommendations;
* recommendation_reasons;
* user_decisions;
* actions;
* outcomes;
* memory;
* events.

⸻

15. RAW_DATA_STORAGE

Если внешняя платформа предоставляет сложные или непредсказуемые данные, желательно сохранять исходный ответ отдельно.

Это позволит:

* повторно обработать данные;
* исправить ошибки нормализации;
* добавить новые признаки;
* провести аудит.

⸻

16. DATABASE VS FILE_STORAGE

Структурированные данные должны находиться в базе.

Большие исходные объекты могут храниться отдельно.

Например:

* изображения;
* видео;
* крупные JSON;
* другие тяжёлые файлы.

База хранит ссылку и метаданные.

⸻

17. DATA_INGESTION_SERVICE

Этот компонент получает данные из внешнего источника.

Основные функции:

* initial import;
* incremental sync;
* обновление статистики;
* обработка ошибок;
* обнаружение новых публикаций;
* предотвращение дубликатов.

⸻

18. INITIAL_IMPORT

После подключения источника система получает исторические данные пользователя.

Это необходимо для формирования первоначальной модели.

Процесс:

connect

↓

authenticate

↓

fetch history

↓

normalize

↓

store

↓

analyze

↓

build initial knowledge

⸻

19. INCREMENTAL_SYNC

После первоначального импорта система не должна каждый раз загружать всю историю.

Она должна получать изменения:

* новые публикации;
* новые показатели;
* обновлённые данные.

Это снижает нагрузку и ускоряет обновление.

⸻

20. PERFORMANCE_REFRESH

Статистика публикаций может изменяться после публикации.

Поэтому система должна периодически обновлять performance data.

Частота обновления может зависеть от:

* возраста публикации;
* активности;
* доступности источника;
* стоимости запроса.

⸻

21. BACKGROUND_JOBS

Тяжёлые операции не должны блокировать пользовательский интерфейс.

В background могут выполняться:

* импорт истории;
* обновление статистики;
* feature extraction;
* pattern detection;
* baseline recalculation;
* skeleton update;
* recommendation recalculation.

⸻

22. JOB_QUEUE

Если объём операций вырастет, фоновые задачи должны проходить через очередь.

Например:

new content

↓

job

↓

analysis

↓

pattern update

↓

recommendation refresh.

Конкретная технология очереди может быть выбрана разработчиком позже.

⸻

23. EVENT_SYSTEM

Система должна фиксировать ключевые события.

Примеры:

* CONTENT_IMPORTED
* PERFORMANCE_UPDATED
* PATTERN_UPDATED
* RECOMMENDATION_CREATED
* RECOMMENDATION_VIEWED
* USER_ACCEPTED
* USER_REJECTED
* ALTERNATIVE_SELECTED
* ACTION_COMPLETED
* OUTCOME_RECEIVED

⸻

24. EVENT_IDEMPOTENCY

Повторная доставка одного события не должна приводить к повторному выполнению критической операции.

Например один и тот же performance update не должен дважды увеличивать статистику.

⸻

25. ANALYSIS_SERVICE

Analysis Service получает структурированные данные и рассчитывает аналитические показатели.

Он отвечает за:

* metric analysis;
* baseline;
* comparisons;
* temporal analysis;
* pattern candidates.

⸻

26. FEATURE_PIPELINE

Feature Pipeline отвечает за извлечение признаков контента.

Архитектура должна позволять добавлять новые анализаторы.

Например:

CONTENT

↓

FORMAT ANALYZER

TOPIC ANALYZER

VISUAL ANALYZER

TEXT ANALYZER

↓

CONTENT_FEATURES

⸻

27. AI_ANALYSIS

AI может использоваться для извлечения некоторых признаков, если это действительно полезно.

Но результат AI-анализа должен сохраняться как:

derived data

с соответствующим confidence.

AI-интерпретация не должна автоматически считаться фактом.

⸻

28. ANALYSIS_VERSION

Результат аналитики должен иметь версию.

Например:

analysis_version = 1

Если алгоритм изменился, новые результаты могут рассчитываться новой версией.

История старых результатов должна сохраняться.

⸻

29. BASELINE_SERVICE

Отдельный модуль рассчитывает персональные baseline.

Он должен поддерживать:

* global baseline;
* format baseline;
* goal-specific baseline;
* temporal baseline.

Не обязательно реализовывать все варианты в MVP.

Архитектура должна позволять их добавить.

⸻

30. PATTERN_SERVICE

Pattern Service отвечает за:

* обнаружение потенциальных закономерностей;
* обновление существующих;
* confidence;
* decay;
* reactivation;
* status.

⸻

31. KNOWLEDGE_STORE

Знания должны храниться отдельно от сырых данных.

Например:

PATTERN

может ссылаться на:

CONTENT

и

PERFORMANCE

но не заменяет их.

⸻

32. DECISION_ENGINE_SERVICE

Decision Engine получает подготовленные данные.

Он не должен самостоятельно обходить всю базу и искать нужную информацию.

Правильная схема:

DATA + ANALYSIS + KNOWLEDGE

↓

DECISION_ENGINE

Это делает Decision Engine предсказуемым и тестируемым.

⸻

33. CANDIDATE_GENERATOR

Отдельный компонент создаёт кандидатов.

В будущем источниками кандидатов могут быть:

* known strong formats;
* historical winners;
* current opportunities;
* experiments;
* user preferences;
* new hypotheses.

⸻

34. SCORING

Каждый кандидат получает внутреннюю оценку.

Оценка должна учитывать:

* goal fit;
* recent performance;
* historical performance;
* freshness;
* pattern strength;
* confidence;
* repetition;
* risk;
* opportunity.

Конкретная формула является частью реализации Decision Engine и может эволюционировать.

⸻

35. DECISION_VERSION

Решение должно сохранять версию алгоритма.

Например:

decision_version

Это позволит сравнивать результаты разных версий Decision Engine.

⸻

36. RECOMMENDATION_SERVICE

После ranking создаётся Recommendation object.

Он содержит:

* primary candidate;
* alternatives;
* goal;
* confidence;
* reasons;
* context;
* timestamp;
* decision version.

⸻

37. EXPLANATION_SERVICE

Explanation Service преобразует структурированные причины в понятный контекст для пользователя.

Он не должен самостоятельно создавать новые факты.

Он работает с уже существующими:

* reasons;
* evidence;
* confidence;
* goal;
* history.

⸻

38. AI_ORCHESTRATION

AI Assistant может использовать отдельный orchestration layer.

Он получает:

USER_MESSAGE

CURRENT_CONTEXT

STRUCTURED_KNOWLEDGE

RECOMMENDATION

и формирует ответ.

⸻

39. AI НЕ ЯВЛЯЕТСЯ DATABASE

AI не должен быть единственным местом хранения пользовательской памяти.

Память должна находиться в структурированной системе.

AI получает необходимую часть памяти в контексте.

Это позволяет:

* контролировать данные;
* обновлять память;
* тестировать;
* менять AI-модель.

⸻

40. AI НЕ ЯВЛЯЕТСЯ DECISION ENGINE

AI может помогать интерпретировать ситуацию, но основной ranking должен происходить в Decision Engine.

Это снижает риск:

* галлюцинаций;
* непоследовательности;
* случайного изменения логики;
* невозможности объяснить решение.

⸻

41. STRUCTURED_CONTEXT

Для AI должен формироваться ограниченный структурированный context package.

Например:

* current goal;
* recommendation;
* top reasons;
* relevant evidence;
* confidence;
* recent actions;
* relevant history.

Ассистенту не нужно передавать всю базу пользователя.

⸻

42. CONTEXT_MINIMIZATION

В AI context следует передавать только необходимую информацию.

Это:

* уменьшает стоимость;
* ускоряет ответы;
* снижает шум;
* уменьшает риск неправильной интерпретации;
* упрощает контроль.

⸻

43. AI_RESPONSE_GUARDRAILS

Перед выдачей ответа система должна по возможности проверять:

* соответствует ли ответ данным;
* не появились ли придуманные факты;
* не утверждается ли неизвестное как факт;
* соответствует ли ответ текущей рекомендации.

⸻

44. USER_FEEDBACK

Пользовательские действия должны возвращаться в backend.

Например:

accepted

→ сохранить.

rejected

→ сохранить.

modified

→ сохранить.

alternative selected

→ сохранить.

Это становится частью learning loop.

⸻

45. OUTCOME_PIPELINE

После публикации или другого действия система получает outcome.

Поток:

ACTION

↓

OUTCOME INGESTION

↓

PERFORMANCE UPDATE

↓

ANALYSIS

↓

KNOWLEDGE UPDATE

↓

RECOMMENDATION REFRESH

⸻

46. RECOMMENDATION_REFRESH

Не каждое изменение должно создавать новую рекомендацию.

Система должна оценивать:

изменилось ли что-то достаточно существенно?

Если нет, текущая рекомендация может остаться.

Если да, ranking пересчитывается.

⸻

47. RECOMMENDATION_EXPIRATION

Рекомендация должна иметь актуальность.

Она может стать устаревшей из-за:

* новой публикации;
* изменения цели;
* новых результатов;
* изменения confidence;
* появления более сильного кандидата.

Устаревшая рекомендация не должна продолжать выглядеть актуальной.

⸻

48. CACHE

Для быстрого UI можно кэшировать:

* current state;
* current recommendation;
* summary analytics.

Но cache не должен становиться единственным источником истины.

⸻

49. CONSISTENCY

Если recommendation обновилась, UI должен получать согласованный набор:

* recommendation;
* reasons;
* confidence;
* alternatives.

Нельзя показывать новую рекомендацию со старыми причинами.

⸻

50. TRANSACTIONAL INTEGRITY

Критические операции должны быть атомарными.

Например создание recommendation и сохранение её ranking должны происходить согласованно.

⸻

51. RETRY

Внешние API и фоновые задачи могут временно падать.

Система должна иметь controlled retry.

Но retry не должен создавать дубликаты.

⸻

52. FAILURE STATES

Система должна различать:

* temporary failure;
* permanent failure;
* unavailable data;
* incomplete data;
* invalid data.

Это позволяет корректно объяснять пользователю состояние системы.

⸻

53. USER EXPERIENCE DURING PROCESSING

Если анализ ещё идёт, пользователь должен видеть понятный статус.

Например:

«Мы анализируем твою историю»

или:

«Обновляем статистику последних публикаций».

Не нужно показывать технические сообщения.

⸻

54. ASYNCHRONOUS_ANALYSIS

Если анализ занимает время, приложение не должно зависать.

Frontend получает состояние:

processing

и может обновить его позже.

⸻

55. OBSERVABILITY

Техническая система должна позволять видеть:

* ошибки;
* latency;
* failed jobs;
* API failures;
* sync failures;
* recommendation generation failures;
* AI failures.

⸻

56. METRICS

Минимально стоит отслеживать:

* время генерации recommendation;
* процент успешной синхронизации;
* количество failed jobs;
* время ответа API;
* ошибки AI;
* время анализа;
* количество stale recommendations.

⸻

57. PRODUCT_ANALYTICS VS SYSTEM_ANALYTICS

Нужно разделять:

PRODUCT_ANALYTICS

как пользователь использует приложение.

SYSTEM_ANALYTICS

как работает сама техническая система.

Они имеют разные цели.

⸻

58. TESTING_ARCHITECTURE

Тестирование должно проходить на нескольких уровнях.

UNIT

отдельные функции.

INTEGRATION

взаимодействие компонентов.

DATA

корректность обработки данных.

DECISION

корректность ranking.

API

корректность контрактов.

UI

основные пользовательские сценарии.

END_TO_END

полный путь:

data → recommendation → user decision → outcome.

⸻

59. DECISION_TESTING

Особое внимание должно уделяться Decision Engine.

Нужно тестировать сценарии:

* сильный video;
* сильный carousel;
* одинаковые кандидаты;
* недостаток данных;
* конфликтующие данные;
* недавнее повторение;
* сильный негативный сигнал;
* новый эксперимент;
* изменение цели;
* изменение baseline.

⸻

60. REPLAY_TESTING

Исторические состояния можно использовать для проверки новых версий Decision Engine.

Например:

«Что бы новая версия системы рекомендовала пользователю месяц назад?»

После этого можно сравнить:

* старое решение;
* новое решение;
* фактический результат.

Это позволит безопаснее улучшать алгоритм.

⸻

61. MODEL_REPLACEMENT

AI-модель должна быть заменяемой.

Система не должна зависеть от одной конкретной модели настолько, чтобы её замена требовала переписывания всего приложения.

⸻

62. PROMPT_VERSIONING

Промпты AI Assistant также должны иметь версии.

Это позволяет понимать:

какой prompt и какая модель сформировали конкретный ответ.

⸻

63. COST_CONTROL

AI и тяжёлая аналитика могут быть дорогими.

Поэтому:

* не нужно отправлять в AI всю историю;
* не нужно запускать тяжёлый анализ без причины;
* повторяющиеся результаты можно кэшировать;
* фоновые процессы можно объединять.

⸻

64. MVP_TECHNICAL_PRINCIPLE

Первая версия должна быть:

простая технически

но

правильная архитектурно.

Не требуется строить сложную распределённую инфраструктуру только ради красивой схемы.

⸻

65. НЕ НУЖНО ДЕЛАТЬ В MVP

Не обязательно сразу реализовывать:

* множество внешних платформ;
* сложную event-driven инфраструктуру;
* отдельный микросервис для каждого блока;
* сложную realtime-систему;
* сложный multi-agent AI;
* большое количество экспериментальных алгоритмов.

Архитектура должна позволять добавить их позже.

⸻

66. MVP МОЖЕТ БЫТЬ МОДУЛЬНЫМ МОНОЛИТОМ

На раннем этапе разумно реализовать систему как один backend с хорошо разделёнными модулями.

Например:

backend

* auth module;
* data module;
* analytics module;
* knowledge module;
* decision module;
* recommendation module;
* assistant module.

Позже отдельные части можно вынести в независимые сервисы, если это действительно понадобится.

⸻

67. ПОЧЕМУ ЭТО ПРАВИЛЬНО

Такой подход позволяет:

* быстрее создать MVP;
* снизить инфраструктурную сложность;
* проще отлаживать;
* сохранить логические границы;
* позже масштабировать отдельные части.

⸻

68. ПРИНЦИП ЗАМЕНЯЕМОСТИ

Если завтра потребуется:

другой AI provider

→ меняется AI adapter.

Если потребуется:

новая социальная платформа

→ добавляется новый connector.

Если потребуется:

новый алгоритм ranking

→ меняется Decision Strategy.

Если потребуется:

новая метрика

→ расширяется Analysis Layer.

Основной продукт при этом продолжает работать.

⸻

69. ПРИНЦИП НЕЗАВИСИМОСТИ

Каждый компонент должен иметь:

* понятный input;
* понятный output;
* ограниченную ответственность;
* тестируемое поведение.

Чем меньше скрытых связей, тем легче развивать систему.

⸻

70. ПРИНЦИП ОБРАТНОЙ СОВМЕСТИМОСТИ

Добавление нового функционала не должно ломать существующие данные.

Новые поля должны быть добавляемыми.

Старые записи должны оставаться читаемыми.

⸻

71. ПРИНЦИП ДАННЫХ КАК ФУНДАМЕНТА

Если UI, AI и Decision Engine временно недоступны, исторические данные всё равно должны оставаться сохранёнными.

Это позволяет восстановить систему.

⸻

72. ПРИНЦИП ОБЪЯСНИМОСТИ

Для каждого важного Recommendation система должна иметь технический trace:

recommendation_id

↓

decision_version

↓

candidate ranking

↓

reasons

↓

evidence

↓

knowledge version

↓

source data

Это техническая основа доверия.

⸻

73. ПРИНЦИП «НЕ ПЕРЕСТРАИВАТЬ РЕСТОРАН»

Каждый новый функциональный блок должен подключаться к архитектуре через существующие границы.

Например:

добавляется новый тип аналитики.

Он не должен заставлять переписывать:

* UI;
* authentication;
* database core;
* Recommendation Engine целиком.

Он должен предоставить новый сигнал в существующую систему.

76. Главный технический принцип

Не строить приложение вокруг конкретной технологии.

Строить его вокруг:

* чётких сущностей;
* чётких границ;
* чётких потоков;
* чётких контрактов;
* проверяемой логики.

Технологии могут меняться.

Архитектурные принципы должны сохраняться.

⸻

77. Итог

TECHNICAL_ARCHITECTURE закрепляет следующий уровень проекта:

мы больше не просто описываем идею приложения.

Мы уже описываем систему, которую можно передать разработчику.

При этом техническая архитектура специально оставляет пространство для будущего роста:

MVP может быть простым.

Логика может быть модульной.

AI можно заменить.

Новые платформы можно подключить.

Новые метрики можно добавить.

Recommendation Engine можно улучшать.

История пользователя остаётся пригодной для нового анализа.

И самое главное:

увеличение возможностей приложения не должно требовать сноса уже построенной системы.
