26_DATA_PIPELINE

1. Назначение документа

DATA_PIPELINE описывает полный жизненный цикл данных внутри системы.

Главный вопрос документа:

что происходит с данными от момента их получения до момента, когда они становятся частью следующего решения системы.

Pipeline должен обеспечивать:

* получение;
* проверку;
* нормализацию;
* сохранение;
* обогащение;
* анализ;
* формирование знаний;
* принятие решений;
* получение результатов;
* обратную передачу результатов в систему.

⸻

2. Главный принцип

Данные не должны превращаться сразу из:

«сырой информации»

в:

«решение».

Между ними должны существовать отдельные этапы.

Основная цепочка:

RAW DATA

↓

VALIDATION

↓

NORMALIZATION

↓

STORAGE

↓

FEATURE EXTRACTION

↓

PERFORMANCE ANALYSIS

↓

BASELINE

↓

PATTERN DETECTION

↓

KNOWLEDGE UPDATE

↓

CANDIDATE GENERATION

↓

DECISION

↓

RECOMMENDATION

↓

USER ACTION

↓

OUTCOME

↓

LEARNING

⸻

3. DATA SOURCES

Источниками данных могут быть:

* внешние социальные платформы;
* пользовательские действия;
* пользовательские настройки;
* внутренние аналитические расчёты;
* AI-derived features;
* результаты экспериментов.

Каждый источник должен иметь понятное происхождение.

⸻

4. RAW_DATA

Система должна по возможности сохранять исходные данные до их преобразования.

Это необходимо для:

* повторной обработки;
* исправления ошибок;
* новой аналитики;
* аудита;
* сравнения версий pipeline.

Raw data не должна использоваться напрямую для принятия пользовательских решений.

⸻

5. INGESTION

Первый технический этап:

получить данные из внешнего источника.

Ingestion отвечает только за доставку данных внутрь системы.

Он не должен одновременно выполнять всю аналитику.

⸻

6. INGESTION_RESULT

Каждый запуск ingestion должен иметь состояние:

* started;
* completed;
* partial;
* failed.

Если часть данных получена, а часть нет, система должна знать об этом.

⸻

7. VALIDATION

После получения данные проходят validation.

Проверяется:

* формат;
* обязательные поля;
* типы;
* идентификаторы;
* даты;
* допустимые значения;
* отсутствие очевидных повреждений.

⸻

8. INVALID_DATA

Некорректные данные не должны автоматически попадать в аналитический слой.

Они должны:

* логироваться;
* маркироваться;
* по возможности отправляться на повторную обработку.

⸻

9. NORMALIZATION

Данные внешних платформ должны приводиться к внутреннему стандарту.

Например разные внешние названия могут преобразовываться в единую сущность:

video

reel

short_video

→

video.

⸻

10. PLATFORM_ADAPTER

Каждая внешняя платформа должна иметь adapter.

Adapter переводит:

EXTERNAL FORMAT

→

INTERNAL FORMAT

Это позволяет остальной системе не зависеть от особенностей конкретной платформы.

⸻

11. DEDUPLICATION

Одна и та же публикация не должна создаваться несколько раз.

Для этого используется комбинация:

* platform;
* external_account_id;
* external_content_id.

⸻

12. DATA_STORAGE

После validation и normalization данные сохраняются в database.

На этом этапе создаются или обновляются:

* content;
* performance;
* snapshots;
* metadata.

⸻

13. INCREMENTAL_PROCESSING

После первоначального импорта pipeline должен преимущественно обрабатывать изменения.

Например:

новая публикация

→ обработать только её.

новая статистика

→ обновить только соответствующую публикацию.

Это значительно эффективнее полного пересчёта всей истории.

⸻

14. CHANGE_DETECTION

Pipeline должен понимать, что именно изменилось.

Например:

* появился новый content;
* изменилась performance;
* изменилась цель;
* появился новый pattern;
* устарел pattern.

Это определяет, какие последующие процессы нужно запускать.

⸻

15. CONTENT_ANALYSIS

Новая публикация проходит анализ.

Могут извлекаться:

* format;
* topic;
* visual features;
* textual features;
* structural features;
* другие признаки.

⸻

16. FEATURE_EXTRACTION

Каждый признак должен иметь:

* value;
* source;
* confidence;
* analysis_version.

Например:

format = video

confidence = high

source = platform

или:

topic = travel

confidence = 0.82

source = AI_ANALYSIS.

⸻

17. AI_DERIVED_DATA

Если признак определён AI, он должен быть явно обозначен как derived.

AI не должен превращать предположение в абсолютный факт.

Например:

не:

topic = travel

а структурно:

topic = travel

source = AI

confidence = 0.82

⸻

18. PERFORMANCE_PIPELINE

Performance может обновляться несколько раз после публикации.

Например:

publication

↓

initial metrics

↓

later metrics

↓

updated metrics

↓

final observed metrics

⸻

19. SNAPSHOT_PRINCIPLE

Каждое существенное измерение может сохраняться как snapshot.

Это позволяет анализировать не только:

«сколько набрала публикация»

но и:

«как она набирала результат».

⸻

20. METRIC_NORMALIZATION

Метрики должны иметь единый внутренний формат.

Например:

* integer;
* percentage;
* duration;
* ratio.

Единицы измерения должны быть однозначны.

⸻

21. MISSING_DATA

Отсутствующая метрика не должна автоматически интерпретироваться как плохой результат.

Pipeline должен различать:

* 0;
* NULL;
* unavailable;
* not_yet_measured.

⸻

22. PERFORMANCE_WINDOW

Для анализа важно понимать возраст публикации.

Например performance через:

* несколько часов;
* 1 день;
* 3 дня;
* 7 дней;
* более длительный период.

Нельзя бездумно сравнивать публикацию, которая существует несколько часов, с публикацией, которая существует месяц.

⸻

23. TIME_ALIGNMENT

Перед сравнением данных pipeline должен учитывать временной контекст.

Например:

content A

измерено через 24 часа

и

content B

измерено через 6 часов

не должны автоматически считаться сопоставимыми.

⸻

24. BASELINE_PIPELINE

После получения performance данные могут использоваться для обновления baseline.

Упрощённо:

PERFORMANCE

→ группировка сопоставимых публикаций

→ расчёт baseline

→ confidence

→ сохранение новой версии.

⸻

25. COMPARABLE_GROUPS

Система должна сравнивать сопоставимые объекты.

Например:

* одинаковый или похожий формат;
* сопоставимая цель;
* сопоставимый период;
* достаточный объём данных.

Это защищает от ложных выводов.

⸻

26. RECENCY_WEIGHT

При анализе система должна учитывать свежесть данных.

Мы уже зафиксировали три уровня:

RECENT

до 3 месяцев.

MEDIUM

от 3 до 6 месяцев.

HISTORICAL

старше 6 месяцев.

Все уровни учитываются.

Но более старые данные имеют меньший вес.

⸻

27. DATA_DECAY

Вес старых данных должен уменьшаться постепенно.

Старый результат не должен внезапно становиться:

«не существует».

Он становится:

менее актуальным доказательством.

⸻

28. PATTERN_DETECTION

После baseline pipeline может запускать поиск закономерностей.

Система ищет:

* повторяющиеся сильные результаты;
* устойчивые слабые результаты;
* комбинации признаков;
* изменения поведения;
* новые emerging patterns.

⸻

29. POSITIVE_PATTERN

Положительная закономерность должна подтверждаться повторяемостью.

Один успешный пост не должен автоматически создавать:

«это всегда работает».

Система должна учитывать:

* количество наблюдений;
* силу результата;
* повторяемость;
* свежесть;
* сопоставимость;
* confidence.

⸻

30. NEGATIVE_PATTERN

Для отрицательных результатов действует тот же принцип.

Система должна различать:

SLIGHTLY_BELOW_BASELINE

результат немного ниже обычного.

CLEARLY_WEAK

результат заметно хуже baseline.

STRONG_FAILURE

результат существенно провалился относительно сопоставимых данных.

Это позволяет понимать не только:

«не сработало»

но и:

«насколько именно не сработало».

⸻

31. PATTERN_CONFIDENCE

Каждая закономерность получает confidence.

Confidence зависит от:

* sample size;
* consistency;
* effect size;
* recency;
* data quality.

⸻

32. PATTERN_LIFECYCLE

Закономерность может проходить стадии:

hypothesis

↓

emerging

↓

confirmed

↓

stable

↓

declining

↓

inactive

Но переходы должны основываться на данных, а не на произвольном времени.

⸻

33. PATTERN_REACTIVATION

Inactive pattern не обязательно удаляется.

Если новые данные снова подтверждают закономерность, она может стать активной.

Это особенно важно для сезонных или циклических паттернов.

⸻

34. SKELETON_PIPELINE

Когда данных становится достаточно, pipeline может обновлять:

CONTENT_SKELETON

Он представляет собой более устойчивую карту:

что у пользователя системно работает лучше всего.

⸻

35. SKELETON_CRITERIA

Pattern может попасть в skeleton, если:

* достаточно данных;
* эффект повторяется;
* confidence высокий;
* pattern не является слишком старым;
* нет сильных противоречащих данных.

⸻

36. SKELETON_UPDATE

Skeleton не должен пересобираться после каждого единичного результата.

Обновление должно происходить при существенном изменении knowledge state.

⸻

37. CANDIDATE_GENERATION

После обновления knowledge система создаёт кандидатов для будущих действий.

Источники:

* strong patterns;
* skeleton;
* recent opportunities;
* experiments;
* user goals;
* новые гипотезы.

⸻

38. CANDIDATE_DIVERSITY

Candidate generation не должен выдавать десять почти одинаковых вариантов.

Система должна сохранять разумное разнообразие.

Например:

* proven format;
* proven topic;
* proven combination;
* controlled experiment.

⸻

39. DECISION_PIPELINE

Кандидаты передаются в Decision Engine.

Для каждого кандидата рассчитываются:

* goal fit;
* expected performance;
* confidence;
* freshness;
* repetition;
* risk;
* opportunity.

⸻

40. DECISION_OUTPUT

Decision Engine возвращает:

* primary candidate;
* alternatives;
* ranking;
* score;
* reasons;
* confidence;
* decision version.

⸻

41. EXPLANATION_PIPELINE

После принятия решения система формирует объяснение.

Оно должно основываться только на имеющихся evidence.

Например:

«Этот формат сейчас рекомендуется, потому что в последних сопоставимых публикациях он стабильно превышал твой baseline по выбранной цели».

⸻

42. USER_INTERACTION

Recommendation показывается пользователю.

Пользователь может:

* принять;
* отказаться;
* изменить;
* выбрать альтернативу;
* отложить.

Каждое действие фиксируется.

⸻

43. USER_DECISION_IS_DATA

Решение пользователя является частью pipeline.

Оно не должно исчезать после отображения recommendation.

Оно становится новым сигналом для системы.

⸻

44. ACTION_PIPELINE

После решения может произойти реальное действие.

Например:

accept

↓

create content

↓

publish

↓

track performance.

⸻

45. OUTCOME_PIPELINE

После действия pipeline ожидает результат.

Результат может приходить постепенно.

Поэтому:

OUTCOME

не является обязательно одной финальной точкой.

⸻

46. LEARNING_LOOP

Ключевая часть всей системы:

RECOMMENDATION

↓

USER DECISION

↓

ACTION

↓

OUTCOME

↓

KNOWLEDGE UPDATE

↓

NEXT RECOMMENDATION

Таким образом система становится циклической.

⸻

47. НЕОБХОДИМОСТЬ REANALYSIS

Не все данные должны анализироваться заново каждый раз.

Reanalysis запускается, когда:

* появился новый существенный объём данных;
* изменился алгоритм;
* изменилась цель;
* обнаружено противоречие;
* pattern потерял confidence;
* требуется исправление данных.

⸻

48. FULL_REBUILD

Иногда необходим полный пересчёт.

Например:

* новая версия анализа;
* существенное изменение методологии;
* исправление ошибки в pipeline.

Full rebuild должен быть возможен.

⸻

49. REPLAY

Система должна по возможности уметь воспроизводить старое состояние.

Например:

«Какой recommendation система сформировала бы на дату X, используя version Y?»

Это особенно важно для развития алгоритма.

⸻

50. PIPELINE_IDEMPOTENCY

Повторный запуск одного этапа не должен создавать дубликаты.

Например повторный ingestion одной публикации не должен создавать вторую публикацию.

⸻

51. PIPELINE_RETRIES

Временные ошибки должны повторяться автоматически.

Например:

* API timeout;
* temporary external error;
* temporary database issue.

Но retry должен быть ограниченным.

⸻

52. DEAD_LETTERS

Если задача не может быть обработана после нескольких попыток, она должна попадать в отдельное состояние для диагностики.

Неудача не должна бесконечно повторяться.

⸻

53. PARTIAL_FAILURE

Если один компонент pipeline упал, вся система не должна автоматически считаться полностью сломанной.

Например:

performance обновилась,

но AI feature extraction временно недоступен.

Система может сохранить performance и дождаться feature analysis позже.

⸻

54. DATA_FRESHNESS

Для каждого важного набора данных желательно знать:

* когда получен;
* когда обновлён;
* насколько свежий;
* какой источник.

Это позволяет Decision Engine учитывать актуальность.

⸻

55. FRESHNESS_STATE

Условно:

fresh

aging

stale

Конкретные пороги могут зависеть от типа данных.

⸻

56. DATA_QUALITY

Каждый pipeline должен учитывать качество входных данных.

Например:

* complete;
* partial;
* suspicious;
* unavailable.

⸻

57. QUALITY_IMPACT

Низкое качество данных должно уменьшать confidence последующего вывода.

Например:

если из 20 публикаций у 8 отсутствует ключевая метрика,

система не должна вести себя так, будто анализ основан на всех 20.

⸻

58. PROVENANCE

Каждый важный аналитический вывод должен иметь путь назад:

recommendation

→ decision run

→ pattern

→ evidence

→ performance

→ source.

Это позволяет объяснить происхождение результата.

⸻

59. VERSIONING

Pipeline должен фиксировать версии:

* ingestion schema;
* analysis version;
* feature version;
* baseline version;
* decision version;
* AI model version;
* prompt version.

⸻

60. PIPELINE_MONITORING

Система должна контролировать:

* сколько данных получено;
* сколько обработано;
* сколько отклонено;
* сколько задач завершилось ошибкой;
* сколько данных устарело;
* сколько analysis jobs выполняется;
* сколько recommendations требуют обновления.

⸻

61. DATA_PIPELINE_DASHBOARD

Внутренний технический dashboard в будущем может показывать:

* sync status;
* last successful ingestion;
* processing queue;
* failed jobs;
* stale data;
* analysis status.

Это необязательно для пользовательского MVP.

⸻

62. COST_AWARE_PROCESSING

Pipeline должен учитывать стоимость обработки.

Дорогие операции не следует запускать:

* без необходимости;
* на неизменившихся данных;
* повторно без причины.

⸻

63. PRIORITY_PROCESSING

Разным задачам можно назначать приоритет.

Например:

HIGH

новая рекомендация для активного пользователя.

MEDIUM

обновление старой статистики.

LOW

глубокий исторический reanalysis.

⸻

64. USER_PRIORITY

Активность пользователя может влиять на приоритет обработки.

Если пользователь прямо сейчас работает с приложением, актуальные данные должны обновляться раньше фонового исторического анализа.

⸻

65. SECURITY

Pipeline не должен смешивать данные разных пользователей.

Каждый пользовательский pipeline запускается в соответствующем user_id context.

⸻

66. PRIVACY

Нужно хранить только те данные, которые действительно нужны продукту.

Не следует сохранять дополнительные персональные данные без необходимости.

⸻

67. DATA_RETENTION

Для разных типов данных могут существовать разные retention policies.

Но:

история, необходимая для аналитики и обучения системы, должна сохраняться достаточно долго, чтобы не разрушать долгосрочное знание.

⸻

68. ОСНОВНОЙ MVP_PIPELINE

Для MVP достаточно следующего:

CONNECT

↓

IMPORT HISTORY

↓

VALIDATE

↓

NORMALIZE

↓

STORE

↓

ANALYZE CONTENT

↓

STORE PERFORMANCE

↓

CALCULATE BASELINES

↓

DETECT PATTERNS

↓

GENERATE RECOMMENDATION

↓

USER DECISION

↓

TRACK OUTCOME

↓

UPDATE KNOWLEDGE

⸻

69. ПОЗДНЕЕ МОЖНО ДОБАВИТЬ

Архитектура должна позволять добавить:

* несколько платформ;
* realtime updates;
* более сложные feature models;
* automated experiments;
* advanced causal analysis;
* более глубокую персонализацию;
* predictive models;
* дополнительные AI-инструменты.

⸻

70. КРИТИЧЕСКОЕ ПРАВИЛО

Ни один единичный результат не должен самостоятельно переписывать знания системы.

Новые данные должны:

1. попасть в pipeline;
2. пройти validation;
3. получить соответствующий вес;
4. быть сопоставлены с историей;
5. изменить confidence только в той мере, в какой это оправдано.

⸻

71. КРИТИЧЕСКОЕ ПРАВИЛО №2

Система должна уметь признавать недостаток данных.

Если evidence недостаточно:

→ confidence снижается.

Если данные противоречивы:

→ это фиксируется.

Если вывод невозможен:

→ система не должна придумывать закономерность.

⸻

72. КРИТИЧЕСКОЕ ПРАВИЛО №3

Старые данные не удаляются только потому, что появились новые.

Они получают меньший вес.

Это позволяет системе помнить историю, но не жить прошлым.

⸻

73. КРИТИЧЕСКОЕ ПРАВИЛО №4

Pipeline должен быть воспроизводимым.

Если одна и та же версия pipeline получает одинаковые входные данные, результат должен быть максимально предсказуемым.

⸻

74. КРИТИЧЕСКОЕ ПРАВИЛО №5

Каждый важный вывод должен иметь происхождение.

Система должна иметь возможность ответить:

«Почему мы сейчас так думаем?»

⸻

76. Главный принцип

Pipeline не просто переносит данные из одной таблицы в другую.

Он превращает:

факты

в

измерения

→ в

сравнения

→ в

закономерности

→ в

знания

→ в

решения

→ в

новые результаты

→ и снова в

знания.

Именно этот замкнутый цикл делает систему обучающейся, а не просто аналитической.
