18_DATA_MODEL

1. Назначение документа

Data Model определяет, какие основные сущности существуют внутри приложения, какие данные они содержат и как связаны между собой.

Если 17-й документ описывает архитектуру системы сверху, то 18-й описывает её внутреннюю структуру.

Главный принцип:

каждый важный объект приложения должен существовать как понятная сущность, а связи между сущностями должны позволять системе восстанавливать полный контекст.

⸻

2. Главная сущность, USER

В центре системы находится пользователь.

User связан практически со всеми основными сущностями.

Пользователь имеет:

* идентификатор;
* профиль;
* цели;
* предпочтения;
* ограничения;
* историю действий;
* контент;
* статистику;
* рекомендации;
* память;
* гипотезы;
* эксперименты.

Все персональные знания должны быть привязаны к конкретному пользователю.

⸻

3. USER_GOAL

Цель пользователя является отдельной сущностью.

Она не должна быть просто текстом в профиле.

Цель содержит:

* тип цели;
* приоритет;
* текущий статус;
* дату создания;
* дату изменения;
* актуальность;
* дополнительные параметры.

Например:

* рост подписчиков;
* рост охватов;
* получение лайков;
* увеличение сохранений.

У пользователя может быть несколько целей одновременно.

⸻

4. GOAL_PRIORITY

Цели могут иметь разный приоритет.

Система должна понимать:

какая цель сейчас наиболее важна.

Приоритет может изменяться со временем.

Recommendation Engine использует актуальные приоритеты при выборе рекомендаций.

⸻

5. CONTENT_ITEM

Каждая публикация пользователя является отдельной сущностью.

Content Item содержит:

* идентификатор;
* пользователя;
* дату создания;
* дату публикации;
* формат;
* тему;
* статус;
* цель публикации;
* ссылку на исходный контент;
* набор характеристик.

Типы могут включать:

* photo;
* video;
* carousel;
* другие форматы в будущем.

Новые форматы не должны требовать перестройки всей модели.

⸻

6. CONTENT_FEATURE

Характеристики контента должны существовать отдельно от самой публикации.

Это позволяет расширять систему новыми признаками.

Feature может описывать:

* наличие текста;
* количество слайдов;
* длительность;
* наличие человека;
* визуальный стиль;
* эмоциональность;
* структуру;
* тему;
* тип подачи;
* другие признаки.

Каждый признак может иметь:

* значение;
* источник;
* уверенность распознавания;
* дату анализа.

⸻

7. CONTENT_FEATURE_SET

Для одной публикации существует набор признаков.

Например:

Content Item

→ carousel

→ 7 slides

→ person present

→ text on first slide

→ personal topic

→ emotional tone

→ short caption

Это позволяет системе анализировать не только отдельные характеристики, но и их комбинации.

⸻

8. CONTENT_ANALYSIS

Результат анализа конкретного контента должен храниться отдельно.

Он содержит:

* какие признаки были обнаружены;
* с какой уверенностью;
* какие категории определены;
* какие комбинации обнаружены;
* какие элементы были неизвестны;
* дату анализа;
* версию анализирующей модели.

Это позволяет в будущем повторно анализировать старый контент улучшенной моделью.

⸻

9. PERFORMANCE_METRIC

Метрики публикации являются отдельными данными.

Основные:

* reach;
* likes;
* saves;
* followers gained.

Комментарии и репосты не являются основными метриками системы.

Для каждой метрики должны храниться:

* значение;
* время измерения;
* источник;
* период измерения.

⸻

10. PERFORMANCE_SNAPSHOT

Показатели публикации могут изменяться со временем.

Например:

через час:

2 000 охвата

через сутки:

10 000

через неделю:

18 000

Поэтому система должна иметь возможность сохранять несколько снимков результата.

Это позволяет анализировать не только итоговый показатель, но и динамику.

⸻

11. PERFORMANCE_CLASSIFICATION

Для каждого результата система определяет его положение относительно нормы пользователя.

Классы:

* far_below_average;
* below_average;
* average;
* above_average;
* strong;
* outstanding;
* anomalous.

Для негативных результатов особенно выделяется:

failure.

⸻

12. GOAL_PERFORMANCE

Одна публикация может иметь разные результаты по разным целям.

Поэтому связь между Content Item и Goal должна быть отдельной.

Например:

Content A

→ reach: outstanding

→ likes: above average

→ saves: strong

→ followers: below average

Это позволяет не сводить эффективность публикации к одному числу.

⸻

13. PATTERN

Pattern является обнаруженной закономерностью.

Он описывает связь между определёнными характеристиками и результатом.

Например:

carousel + text_on_first_slide → high saves

Pattern содержит:

* описание;
* связанные признаки;
* связанную цель;
* направление влияния;
* количество наблюдений;
* количество подтверждений;
* уровень уверенности;
* временной вес;
* текущий статус.

⸻

14. POSITIVE_PATTERN

Положительная закономерность указывает на связь с более высоким результатом.

Например:

личная фотография + короткий текст → высокий уровень лайков.

Она не обязательно означает причинность.

До подтверждения система должна относиться к ней как к статистической закономерности или гипотезе.

⸻

15. NEGATIVE_PATTERN

Отрицательная закономерность указывает на связь с более слабым результатом.

Например:

формат X + тема Y → результат значительно ниже обычного.

Она также требует достаточного количества наблюдений.

⸻

16. PATTERN_CONFIDENCE

Каждая закономерность должна иметь уровень уверенности.

Он зависит от:

* количества наблюдений;
* повторяемости;
* согласованности результатов;
* свежести;
* количества исключений;
* качества исходных данных.

Система должна отличать:

«мы подозреваем»

от:

«это стабильно подтверждается».

⸻

17. HYPOTHESIS

Гипотеза появляется, когда система замечает потенциальную закономерность, но данных ещё недостаточно.

Например:

«Текст на первом слайде может увеличивать сохранения».

Гипотеза может:

* подтверждаться;
* ослабевать;
* опровергаться;
* переходить в Pattern.

⸻

18. EXPERIMENT

Эксперимент используется для проверки гипотезы.

Он содержит:

* гипотезу;
* цель;
* тестируемый фактор;
* предполагаемый результат;
* публикации, участвующие в тесте;
* фактический результат;
* вывод.

Таким образом система может не просто наблюдать, но и учиться через контролируемые проверки.

⸻

19. RECOMMENDATION

Recommendation является конкретным предложением пользователю.

Она содержит:

* идентификатор;
* пользователя;
* цель;
* предлагаемое действие;
* причины;
* связанные закономерности;
* уровень уверенности;
* приоритет;
* время создания;
* срок актуальности;
* статус.

⸻

20. RECOMMENDATION_STATUS

Рекомендация может иметь состояние:

* generated;
* shown;
* accepted;
* rejected;
* modified;
* postponed;
* completed;
* expired.

Это позволяет системе понимать судьбу каждой рекомендации.

⸻

21. RECOMMENDATION_REASON

Каждая важная рекомендация должна иметь объяснимую основу.

Recommendation Reason может ссылаться на:

* Pattern;
* Performance;
* Goal;
* User Context;
* Experiment;
* recent behavior.

Например:

«Последние 5 похожих публикаций дали высокий уровень сохранений».

⸻

22. USER_DECISION

Решение пользователя является самостоятельной сущностью.

Система должна хранить:

* что было предложено;
* когда;
* что выбрал пользователь;
* изменил ли он предложение;
* отказался ли;
* почему, если причина известна;
* что произошло после решения.

Это позволяет анализировать взаимодействие пользователя с системой.

⸻

23. USER_ACTION

Действие пользователя шире, чем решение по рекомендации.

Например:

* опубликовал;
* изменил формат;
* создал эксперимент;
* изменил цель;
* изменил предпочтение;
* запросил помощь;
* отклонил рекомендацию.

Это является частью истории поведения пользователя.

⸻

24. MEMORY_ITEM

Memory Item является отдельным элементом памяти пользователя.

Он может содержать:

* предпочтение;
* факт;
* цель;
* закономерность;
* сильную сторону;
* слабую сторону;
* решение;
* контекст;
* историю.

Каждый Memory Item должен иметь:

* источник;
* дату;
* уверенность;
* временной вес;
* актуальность.

⸻

25. MEMORY_WEIGHT

Информация имеет временной вес.

Базовая модель:

0–3 месяца → высокий вес

3–6 месяцев → средний вес

6+ месяцев → пониженный вес

Старая информация не удаляется автоматически.

⸻

26. USER_STRENGTH

Сильная сторона пользователя является отдельной аналитической сущностью.

Например:

«Пользователь особенно хорошо получает сохранения через образовательные карусели».

Сильная сторона должна иметь:

* основание;
* количество подтверждений;
* уровень уверенности;
* актуальность.

⸻

27. USER_WEAKNESS

Аналогично система может хранить слабые стороны.

Например:

«Видео определённого типа стабильно дают результат ниже среднего».

Это не должно быть обвинением или окончательным диагнозом.

Это аналитический сигнал, который может измениться при появлении новых данных.

⸻

28. USER_CONTEXT

User Context объединяет текущую ситуацию пользователя.

Например:

* текущая цель;
* недавние публикации;
* активные эксперименты;
* актуальные закономерности;
* текущие ограничения;
* последние решения;
* последние рекомендации.

Это динамический слой, который меняется значительно чаще, чем долгосрочная память.

⸻

29. DAILY_STATE

Система должна иметь понятие текущего состояния пользователя на конкретный день.

Daily State может включать:

* текущую главную цель;
* актуальную рекомендацию;
* последние действия;
* новые данные;
* изменения закономерностей;
* состояние активных экспериментов.

Это помогает реализовать принцип:

каждый день система показывает наиболее актуальную информацию.

⸻

30. CONTENT_GROUP

Content Group позволяет объединять похожие публикации.

Группа может формироваться по:

* формату;
* теме;
* визуальным признакам;
* цели;
* комбинациям характеристик.

Например:

personal_carousel_with_text

может стать отдельной группой, если данных достаточно.

⸻

31. PATTERN_EVIDENCE

Каждая закономерность должна иметь доказательную базу.

Evidence может ссылаться на конкретные публикации.

Например:

Pattern:

carousel + text → strong saves

Evidence:

* Content 12;
* Content 18;
* Content 27;
* Content 41;
* Content 52.

Это позволяет системе восстановить, откуда взялся вывод.

⸻

32. ANALYTICAL_EVENT

Некоторые события должны сохраняться как аналитические события.

Например:

* новая публикация;
* получение статистики;
* изменение цели;
* появление новой закономерности;
* изменение уверенности;
* принятие рекомендации;
* отказ;
* завершение эксперимента.

Это помогает строить историю изменений.

⸻

33. DATA_SOURCE

Каждый внешний или внутренний факт должен иметь источник.

Например:

* пользователь;
* социальная платформа;
* Content Analysis;
* Analytics;
* AI Assistant;
* Recommendation Engine.

Это повышает объяснимость и позволяет проверять данные.

⸻

34. DATA_QUALITY

Система должна понимать качество данных.

Для данных можно хранить:

* confidence;
* completeness;
* source;
* timestamp;
* validation status.

Особенно важно различать:

значение отсутствует

и:

система не смогла его определить.

⸻

35. VERSION

Модели анализа могут улучшаться.

Поэтому результат анализа должен быть связан с версией модели.

Например:

Content Analysis v1

позже:

Content Analysis v2

Старые результаты не обязательно удалять.

Новая модель может повторно анализировать старый контент.

38. Почему Data Model должна быть расширяемой

Новые функции не должны требовать разрушения существующих сущностей.

Например, если появится новый формат контента:

short_form_audio

его можно добавить как новый тип Content Item.

Если появится новая метрика:

profile_visits

её можно добавить в систему Performance Metrics.

Если появится новая цель:

brand_awareness

она становится новым Goal Type.

Базовые связи остаются прежними.

⸻

39. Принцип гибкости признаков

Content Features должны быть особенно гибкими.

Мы заранее не знаем все признаки, которые окажутся полезными.

Поэтому модель должна позволять добавлять новые характеристики без изменения структуры всей системы.

Это особенно важно для самообучающегося Content Analysis Engine.

⸻

40. Разделение фактов, наблюдений и выводов

Это один из важнейших принципов Data Model.

Система должна различать:

FACT

Например:

публикация получила 20 000 охвата.

OBSERVATION

Например:

публикации с текстом на первом слайде часто получают больше сохранений.

HYPOTHESIS

Например:

текст на первом слайде может повышать сохранения.

PATTERN

Например:

закономерность подтверждается на достаточном количестве публикаций.

RECOMMENDATION

Например:

сейчас стоит попробовать карусель с текстом на первом слайде.

Эти сущности нельзя смешивать.

⸻

41. Разделение истории и текущего состояния

Система должна хранить одновременно:

историю

и

текущее состояние.

История отвечает:

«что происходило?»

Текущее состояние отвечает:

«что актуально сейчас?»

Это особенно важно для ежедневных рекомендаций.

⸻

42. Исторические данные не исчезают

Старая публикация продолжает существовать в системе даже после того, как её влияние на текущие рекомендации снизилось.

Это позволяет:

* изучать долгосрочные закономерности;
* сравнивать периоды;
* обнаруживать возвращение старых тенденций;
* анализировать эволюцию пользователя.

⸻

43. Система должна поддерживать пересчёт

Если алгоритм анализа изменился, данные не должны становиться бесполезными.

Например:

новая версия Content Analysis обнаружила новый признак.

Система может:

повторно проанализировать старые публикации → обновить признаки → пересчитать закономерности → обновить рекомендации.

⸻

44. Объяснимость через связи

Любая важная рекомендация должна теоретически позволять пройти назад по цепочке:

Recommendation

↓

Reason

↓

Pattern

↓

Evidence

↓

Content

↓

Performance

То есть система должна иметь возможность ответить:

«Почему ты мне это рекомендуешь?»

не выдумывая объяснение задним числом.

⸻

45. Минимальная версия Data Model

Для первого MVP достаточно основных сущностей:

* User;
* Goal;
* Content;
* Content Feature;
* Performance Metric;
* Pattern;
* Memory;
* Recommendation;
* User Decision;
* Experiment.

Остальные сущности могут быть реализованы постепенно.

⸻

46. Главный принцип Data Model

Data Model должна позволять системе сохранить не только:

что произошло,

но и:

что система об этом подумала, насколько она уверена, почему она так решила и что произошло после этого.

Это превращает приложение из обычной аналитической системы в обучающуюся персональную систему принятия решений.

⸻

48. Главный принцип проекта

Приложение должно хранить не просто данные о пользователе, а историю того, как система постепенно пришла к своему пониманию пользователя.

Поэтому Data Model должна сохранять связь:

факт → наблюдение → гипотеза → доказательства → закономерность → рекомендация → решение → результат.

Именно эта цепочка со временем становится интеллектуальным капиталом приложения.
